# TradeRath Backend

The primary backend is a FastAPI application. The `pocketbase/` directory is a
temporary compatibility layer for the existing frontend data model; do not add
new product functionality there. New API code belongs in `app/` and tests belong
in `tests/`.

## Setup

```bash
python -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements-dev.txt
uvicorn app.main:app --reload --port 8000
```

## Test

```bash
python -m pip install -r requirements-dev.txt
python -m pytest
```

Use Python 3.12, matching backend CI. In Windows Git Bash, activate a virtual
environment with `source .venv/Scripts/activate` (or `.trade_env/Scripts/activate`
if that is your existing environment).

Tests get a fresh application through `create_app()` and a function-scoped
`client` fixture. The client context runs application startup/shutdown, following
the [FastAPI lifespan testing guidance](https://fastapi.tiangolo.com/advanced/testing-events/).
Tests set their own CORS configuration and do not call a running backend,
PocketBase, or external providers. Add provider fakes when integrations arrive.

For each behavior, add a failing test, run it to confirm the expected failure,
implement the change, and run the complete suite before committing. Integration
tests require a dedicated PostgreSQL test database as described below.

The `Backend tests` GitHub Actions workflow runs on PRs, pushes to `main`, and
manual dispatch. It installs dependencies, checks their compatibility, and runs
pytest on Python 3.12 using [GitHub's Python setup approach](https://docs.github.com/en/actions/tutorials/build-and-test-code/python).
The workflow is repository automation; backend code and dependencies remain here.

## Core API configuration

Set `APP_ENV` to `development`, `test`, or `production`. `CORS_ORIGINS` accepts
comma-separated HTTP(S) origins without paths; production origins require HTTPS.
An empty list disables cross-origin browser access. Settings are validated when
the app is created. Environment files are not loaded implicitly; use Uvicorn's
`--env-file .env` option if needed (never commit that file).

Run from `backend/` with structured access logging:

```bash
uvicorn app.main:app --reload --port 8000 --log-config logging.json --no-access-log
```

The logging configuration disables raw Uvicorn access logs, which otherwise
include URL query strings. Application access events contain only generated
request IDs, HTTP methods, route templates, status, and elapsed milliseconds.
They omit headers, bodies, query strings, concrete path parameters, and exception
messages. Configure deployment proxy logs separately to apply the same policy.

Both `/health` and `/api/v1/health` report process liveness. Database readiness
is checked by `/health/ready` (200 when reachable, otherwise 503). This checks
connectivity, not whether migrations have been applied. Handled API failures use
`{"error":{"code":"...","message":"...","request_id":"..."}}`.
Request IDs are generated by the server and exposed through `X-Request-ID`.
CORS preflight responses are handled directly by the CORS middleware.

## PostgreSQL setup and migrations

Use PostgreSQL 17 and provision two empty databases, `traderath_dev` and
`traderath_test`, owned by a dedicated development role. The application never
creates databases or automatically migrates them at startup. Do not use a
production database for tests or a superuser as the deployed application role.

Set `DATABASE_URL` and `TEST_DATABASE_URL` in your local environment or ignored
`backend/.env`; see `.env.example`. Both use `postgresql+psycopg://`. Percent-encode
special characters in usernames/passwords. Do not commit credentials. The test
database name must end in `_test`. Tests create and drop only their own randomly
named schemas; the role needs permission to create schemas in that database.

Run these commands from `backend/` after setting the variables:

```bash
python -m pip install -r requirements-dev.txt
python -m alembic upgrade head
python -m alembic current
python -m pytest
```

If using `.env`, commands can instead be wrapped without printing credentials:

```bash
python -c "from dotenv import load_dotenv; load_dotenv('.env'); from alembic.config import main; main(argv=['upgrade', 'head'])"
python -c "from dotenv import load_dotenv; load_dotenv('.env'); import pytest; raise SystemExit(pytest.main())"
```

Without `TEST_DATABASE_URL`, integration tests skip locally; CI requires it and
provides an ephemeral PostgreSQL service. Unit tests never use `DATABASE_URL`.
The initial migration creates users, organizations, memberships, and sessions
with foreign keys, role/expiry constraints, and case-insensitive unique emails.
Authentication, tenant-scoped business queries, last-owner protection, and account
recovery will be implemented in subsequent branches.

Use `Depends(get_session)` from `app.db.session` in synchronous database endpoints.
Services own transactions via `with session.begin():`; the request dependency
closes sessions and rolls back unfinished work. Never rely on an implicit commit
after a response. Engines are scoped to application lifespan and disposed on
shutdown. Pool and connection/statement waits are bounded.

Generate future migrations with `python -m alembic revision --autogenerate -m
"description"`, inspect the generated SQL changes, and run upgrade tests.
`python -m alembic downgrade base` removes identity tables and their data; only
use it on a disposable database. Production releases require backups and a
reviewed rollback plan. See [Alembic migrations](https://alembic.sqlalchemy.org/en/latest/tutorial.html)
and [SQLAlchemy transactions](https://docs.sqlalchemy.org/en/20/orm/session_basics.html).

## Legacy PocketBase development

Install the version recorded in `pocketbase/.pocketbase-version` separately and
place the executable on `PATH`; its executable and local `pb_data` directory must
not be committed. The demo-data migration requires the
`TRADERATH_DEMO_USER_PASSWORD` environment variable. Never use a production
credential for local seed data.
